# Vibecoding Project Tracker — Product Requirements Document

**Status:** Milestone 12 Final Revision — Functional, Non-Functional and Data Requirements (`prd-done`).

Individual hackathon project: a single-page Kanban board for vibecoding tasks that preserves the AI prompt context behind each task. Stack: React + TypeScript (Vite) + Tailwind CSS, with client-side persistence via localStorage. FR-01–FR-18 originate from the initial requirements phase and are preserved unchanged. FR-19 — originally written during planning as the open-ended M12 "Secret Sauce" — and the new FR-20 are specified here retrospectively from the completed M12 implementation (Project Health Dashboard and Demo Login); FR-21 documents the Kanban Drag & Drop enhancement added to M12 afterwards. They were not written explicitly during the initial planning phase. The Data Requirements section (§3) formally documents the data needs of the finished prototype — original M4–M11 features and the M12 enhancements — as they are actually implemented.

## 1. Functional Requirements

**MVP** = required in the demo-ready product. FR-01–FR-18 are MVP. The only non-MVP items are FR-19, FR-20 and FR-21 — the enhancements completed in M12.

| ID | Requirement | MVP | Milestone |
|---|---|---|---|
| FR-01 | The app renders a Kanban board with exactly four columns, in the order **To Do, In Progress, Review, Done**, using the fixed stage IDs `todo`, `in-progress`, `review`, `done`. | Yes | M4 |
| FR-02 | Each task is displayed as a card in the column matching its current status. On first load the board shows 3–4 seed tasks, so it is never empty. | Yes | M4 |
| FR-03 | The user can change a task's status, and the card moves to the corresponding column immediately. | Yes | M4 |
| FR-04 | Each task stores exactly these fields: `id`, `title`, `description`, `type` (`feature` or `bug`), `status`, `assignee`, `dueDate` (nullable, ISO `YYYY-MM-DD`), `createdDate` (ISO `YYYY-MM-DD`). | Yes | M4 |
| FR-05 | The user can create a task through a modal that captures title, description, type, assignee and optional due date; the new card appears on the board. | Yes | M5 |
| FR-06 | The user can edit every field of an existing task through the same modal; saving updates the card on the board. | Yes | M5 |
| FR-07 | The user can delete a task after an explicit confirmation step; the card is removed from the board. | Yes | M5 |
| FR-08 | Tasks and anchors persist in browser localStorage and survive a full page refresh without data loss. | Yes | M5 |
| FR-09 | Feature and bug tasks are visually distinguishable: cards use distinct color tokens per type (accent stripe and icon). | Yes | M6 |
| FR-10 | Every card displays its assignee as a badge. | Yes | M7 |
| FR-11 | The user can reassign a task via a "Hand off to..." dropdown. Selectable values are exactly the three demonstration roles: `Solo Developer`, `Demo Reviewer`, `Demo Designer`. | Yes | M7 |
| FR-12 | Card colors automatically reflect due-date urgency: done tasks are neutral; otherwise **safe** when more than 2 days out, **warning** when less than 24 hours out, **overdue** when past the due date. | Yes | M8 |
| FR-13 | The task modal provides a Context field that accepts Markdown-formatted text (the curated briefing for the next AI session or reviewer). | Yes | M9 |
| FR-14 | Saving the context records a `contextUpdatedAt` ISO timestamp automatically; every save refreshes the timestamp. | Yes | M9 |
| FR-15 | The modal offers an optional AI tool selector with exactly the values `Claude`, `ChatGPT`, `Cursor`, `Lovable`, `Replit`, `Other`. | Yes | M9 |
| FR-16 | A "Copy as Prompt Context" action serializes the task fields plus the context into a formatted Markdown block and copies it to the clipboard. | Yes | M10 |
| FR-17 | A Deliverable Anchor Board pinned above the Kanban displays exactly four slots: **Presentation, Demo, Report, Documentation**. | Yes | M11 |
| FR-18 | Each anchor slot allows adding, editing and saving a link; saved links persist in localStorage. | Yes | M11 |
| FR-19 | **Project Health Dashboard:** a collapsible dashboard rendered above the Kanban board (between the Deliverable Anchor Board and the workload strip), open by default with a "Hide/Show Project Health" toggle. It shows five live statistics computed from the current task list: **Total Tasks**, **Completed Tasks** (status `done`), **Completion Percentage** (completed ÷ total, rounded to a whole number, 0 on an empty board), **Overdue Tasks** (same due-date rules as FR-12, so done tasks are never counted) and **Active Bugs** (bug-type tasks not in `done`). An overall completion progress bar mirrors the percentage and repeats the number as text so it is never conveyed by the bar alone. All values are derived at render time from the stored task data and the current local date — nothing is stored separately — and every create, edit, delete, status or type change updates the dashboard immediately. | No | M12 |
| FR-20 | **Demo Login:** until a session exists the app shows a demo login screen instead of the board. Signing in with the fixed demonstration credentials defined in `src/data/constants.ts` (shown openly on the login page for assessors) or clicking "Continue as Demo" opens the board; wrong credentials show a single generic error message. The session is recorded only as a `vibetracker.demoSession` flag in sessionStorage — tab-scoped, surviving a refresh but cleared by "Log out" or closing the tab; the password is never persisted. Logging in never resets or reseeds task or anchor data. This is a demonstration gate, not real authentication: it adds no backend and does not protect the stored project data. | No | M12 |
| FR-21 | **Kanban Drag & Drop:** the **entire task card** is draggable with the left mouse button — the six-dot grip remains purely as a visual affordance, and a drag can start anywhere on the card body. Pressing and holding the card, then moving, starts the drag; a click without movement opens the edit modal. The user can drag a card from any column into any other column in any direction, reorder cards within a column by dropping above or below a target card or at the bottom, and drop into empty columns. Dragging must not start from the card's interactive controls (status dropdown, handoff dropdown, Copy as Prompt Context button or any other button/link/form control — they stay clickable), and a completed drag never accidentally opens the edit modal. A cross-column drop updates the task's `status` to the destination column through the same state path as the status dropdown; every other task field (including AI context and timestamps) is preserved. While dragging, the destination column is highlighted and a brand-primary insertion line shows the exact drop position. Card order within each column is stored in a separate `vibetracker.taskOrder` id list (the locked `Task` model is unchanged) and survives a refresh; new tasks are placed at the top of their column, deleted tasks' ids are pruned, and tasks missing from the list stay visible at the bottom of their column. The existing status dropdown remains available and is the accessible alternative to dragging; a successful move is announced through the existing toast (`role="status"`). Drag interactions must meet the existing NFRs (NFR-02 responsiveness, NFR-03 persistence, NFR-06 accessibility via the status dropdown). | No | M12 |

## 2. Non-Functional Requirements

| ID | Requirement | MVP | Verification |
|---|---|---|---|
| NFR-01 | **Usability** — A new user can add a task, edit it and move it between columns without instructions. Primary actions ("+", "Copy as Prompt Context", "Hand off to...") use plain-language labels in a single visible area. | Yes | Manual walkthrough: complete the primary flow (add → move → copy) in under 2 minutes. |
| NFR-02 | **Performance** — All interactions (opening the modal, moving a task, copying the prompt) respond within 200 ms on a board of up to 50 tasks, with no full-page reloads. | Yes | Manual timing check during the demo with the seed dataset. |
| NFR-03 | **Persistence** — Task and anchor data survives page refreshes and browser restarts via localStorage; no backend involved. | Yes | Refresh and fully restart the browser; verify the board state is unchanged. |
| NFR-04 | **Compatibility** — The app runs correctly in current desktop versions of Chrome, Edge and Firefox. | Yes | Manual smoke test in each browser: board renders and CRUD works. |
| NFR-05 | **Reliability** — Normal editing, moving and deleting must never lose or corrupt stored data; localStorage is written on every state change. | Yes | Manual CRUD session followed by a reload integrity check. |
| NFR-06 | **Accessibility** — Body text meets WCAG AA contrast (≥ 4.5:1); every form control has an associated label; the board and modal are keyboard-operable. | Yes | Contrast check of the design tokens + manual keyboard navigation. |
| NFR-07 | **Maintainability** — The UI is composed of reusable React components (e.g. Column, TaskCard, TaskModal, AnchorBoard); colors are applied only through the Tailwind design tokens in `tailwind.config.js`. | Yes | Code review against the component list and token usage. |
| NFR-08 | **Deployability** — The production build completes without errors and the app deploys to Vercel at a public URL that loads without console errors. | Yes | Successful `npm run build` + deployed URL loads cleanly. |
| NFR-09 | **Simplicity** — No backend, authentication or runtime dependency beyond React, Vite and Tailwind CSS (plus the TypeScript dev toolchain); all data stays client-side. | Yes | `package.json` review. |

**Clarification on NFR-09 (M12):** the Demo Login (FR-20) does not conflict with this requirement. It adds no backend and no real authentication — the credentials are hard-coded constants compared in the browser, the only persisted login state is a temporary sessionStorage flag, and `package.json` still lists no runtime dependency beyond React, Vite and Tailwind CSS. The login is for demonstration purposes only: it demos a sign-in flow for assessors and is not production-grade authentication.

## 3. Data Requirements

This section documents the data the completed prototype actually requires, derived from the implementation and the locked `Task` / `Anchor` data model in `src/types/task.ts`. Exactly four persistence surfaces exist — there is no backend and no database:

- **`vibetracker.tasks`** (localStorage, JSON) — the full task array, including each task's AI context fields.
- **`vibetracker.anchors`** (localStorage, JSON) — the four deliverable anchor slots.
- **`vibetracker.taskOrder`** (localStorage, JSON) — the drag-and-drop card ordering (an array of task ids, kept out of the locked `Task` model).
- **`vibetracker.demoSession`** (sessionStorage) — the temporary M12 demo-login flag.

Everything else is either predefined configuration shipped in source code (stage IDs, team roles, AI tool list, seed tasks, anchor defaults, demo credentials) or calculated at render time (due-date urgency states, Project Health statistics, the copied prompt). Calculated values are never stored separately from the data they derive from. Each row below records the data's source, why it is needed, where it lives, its MVP status and the functional requirements it supports; milestone ownership (M4–M12) is traceable through the Milestone column of the FR table in §1, and NFR-03/NFR-05 set the persistence and reliability expectations the storage keys above must meet.

| ID | Data Requirement | Data Source | Purpose / Justification | Storage / Format | MVP | Related FR |
|---|---|---|---|---|---|---|
| DR-01 | Unique task identifier (`Task.id`, string) that never changes for the life of the task. | System-generated: `crypto.randomUUID()` for user-created tasks (timestamp-based fallback); fixed readable IDs (e.g. `seed-prd-review`) for the four seed tasks. | Lets the app target one specific task for status moves, reassignment, editing, deletion and prompt copying without ambiguity. | Persisted as a field of each `Task` in `vibetracker.tasks` (localStorage, JSON array). | Yes | FR-04, FR-05, FR-06, FR-07 |
| DR-02 | Task title — required single-line text, saved trimmed and never empty. | User input (task modal). | Identifies the task on the card, in the modal and in the copied prompt; the primary scan cue on the board. | Field of each `Task` in `vibetracker.tasks`. | Yes | FR-04, FR-05, FR-06, FR-16 |
| DR-03 | Task description — optional free text describing what the task involves. | User input (task modal). | Carries the task detail the title cannot; included verbatim in the copied prompt (FR-16). | Field of each `Task` in `vibetracker.tasks`. | Yes | FR-04, FR-05, FR-06, FR-16 |
| DR-04 | Task type — one of the predefined values `feature` or `bug`. | Predefined options selected via the modal dropdown (default `feature`). | Drives the M6 visual distinction (accent stripe, icon, badge) and the Active Bugs dashboard metric (FR-19). | Field of each `Task` in `vibetracker.tasks`. | Yes | FR-04, FR-05, FR-06, FR-09, FR-19 |

| DR-06 | Assignee — one of the three demonstration roles `Solo Developer`, `Demo Reviewer`, `Demo Designer`. | Predefined options (modal dropdown or the card's "Hand off to" dropdown). | Displays ownership on every card (FR-10), enables reassignment (FR-11) and powers the team workload strip. | Field of each `Task` in `vibetracker.tasks`. | Yes | FR-04, FR-05, FR-06, FR-10, FR-11 |

| DR-08 | Due date — optional deadline, ISO `YYYY-MM-DD`, or `null` when none is set. | User input (modal date picker); optional. | Drives the M8 urgency tints and labels (FR-12), the Overdue dashboard metric (FR-19) and the due date shown on the card. | Field of each `Task` in `vibetracker.tasks`. | Yes | FR-04, FR-05, FR-06, FR-12, FR-19 |
| DR-09 | Seed task dataset — four predefined demo tasks (one per stage) that populate the board on first load. | Predefined constants in `src/data/seedTasks.ts` (system-provided). | Guarantees the board is never empty (FR-02) and gives the demo a realistic starting state. | Written to `vibetracker.tasks` only on first load when no stored value exists; never re-inserted afterwards. | Yes | FR-02, FR-08 |
| DR-10 | AI context text — Markdown-formatted briefing saved with each task. | User input (modal Context textarea); saved verbatim (line breaks included, not trimmed); defaults to the empty string. | Preserves the curated prompt/briefing between sessions (FR-13) and is embedded verbatim in the copied prompt (FR-16). | Field of each `Task` in `vibetracker.tasks`. | Yes | FR-13, FR-14, FR-16 |
| DR-11 | Selected AI tool — the assistant the context targets: `Claude`, `ChatGPT`, `Cursor`, `Lovable`, `Replit`, `Other`, or `null` for None. | Predefined options in the modal AI Tool dropdown. | Records which tool the briefing was prepared for; included in the copied prompt when set. | Field of each `Task` in `vibetracker.tasks`. | Yes | FR-15, FR-16 |
| DR-12 | Context last-updated timestamp — ISO timestamp of the last save that changed the context text or the AI tool. | System-generated automatically on save (`new Date().toISOString()`); `null` until the first context save; untouched by saves that only change other fields. | Tells the user how current the briefing is (FR-14) and appears in the copied prompt. | Field of each `Task` in `vibetracker.tasks`. | Yes | FR-14, FR-16 |

| DR-18 | Project Health statistics — Total Tasks, Completed Tasks, Completion Percentage, Overdue Tasks, Active Bugs, plus the overall completion bar. | Derived: calculated live from the stored task list at render time by `calculateProjectHealth()`; Overdue reuses the FR-12 due-state rules, so done tasks are never counted. | Powers the M12 dashboard without duplicating or separately storing any data. | Not stored — recalculated on every render, so every create, edit, delete, status or type change updates the dashboard immediately. | No | FR-19 (consumes task data of FR-03–FR-08, FR-12) |
